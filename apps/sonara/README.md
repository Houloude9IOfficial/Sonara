# Sonara app

The shared Flutter shell targets Windows and Android. On Windows, the native runner discovers visible application processes and active LAN interfaces, starts the bundled Rust/WASAPI host, and owns notification-area/background lifecycle. While pairing is open, the host answers active UDP discovery probes and sends bounded LAN beacons on port 49813. Android listeners discover these sessions automatically; validated manual invitation entry remains a fallback. Connecting starts `SonaraService`, a media-playback foreground service. The service calls the Rust receiver through JNI; Rust owns QUIC authorization, clock exchange, packet validation, and reordering, while the C++ Oboe adapter owns the callback and bounded render ring. Audio samples never pass through Dart.

Build the Windows portable app with `flutter build windows --release`; launch `build/windows/x64/runner/Release/sonara.exe`. The build also compiles and bundles the internal `sonara_engine.exe`, so users do not run Cargo or enter a PID/IP address. Build Android with `flutter build apk --debug`; Gradle invokes `cargo ndk` for `arm64-v8a` and `x86_64` automatically.

The default Low Delay + Balanced profile starts at a 20 ms software queue and adapts up to 60 ms only after real underruns. Ultra Low uses a 10–30 ms range; platform and network latency are additional. The receiver waits for the real Oboe callback before releasing host audio, performs a single bounded refill instead of repeatedly stuttering, shrinks its target after a stable interval, skips stale frames after platform pauses, holds CPU/high-performance Wi-Fi locks only while its foreground service is active, and reports underruns, recovery events, inserted silence frames, and stale-frame skips separately.
